# Technical Compatibility Matrix

**Audit date:** 2026-11-05 (UTC).  
**Interpretation:** “Documentation checked” means official documentation was read; it is not an application build or compatibility test. SAP Core package versions and an application lockfile are not present, so no app-level combination can be marked compatible or tested.

## Database, ORM, and authentication

| Component / concern | Official evidence reviewed | Result for SAP Core | Required verification |
|---|---|---|---|
| Prisma Postgres platform | [Prisma Postgres](https://www.prisma.io/docs/postgres) | Current docs describe managed PostgreSQL 17, PgBouncer pooling, and a direct connection path for migrations. This is a documented provider baseline, not evidence that an instance has been provisioned or that a specific plan/configuration was selected. | Pin the provider/runtime connection setup; distinguish pooled application URL from direct migration URL; inspect current backup, TLS, and plan behavior before production. |
| PostgreSQL engine | [PostgreSQL 17 constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [numeric types](https://www.postgresql.org/docs/17/datatype-numeric.html), [date/time](https://www.postgresql.org/docs/17/datatype-datetime.html), [isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [sequences](https://www.postgresql.org/docs/17/functions-sequence.html) | PostgreSQL 17 is the provider version documented for Prisma Postgres as of this audit. PostgreSQL documentation confirms exact `numeric`, date-only `date`, UTC-normalized `timestamptz`, row-lock behavior, isolation failure/retry requirements, nullable-constraint behavior, and non-transactional sequence gaps. | Confirm the actual service major at implementation. Use version-matched documentation and test target SQL, time mapping, rounding, constraints, lock/retry behavior, and sequence policy. |
| Prisma ORM multi-schema | [Multi-schema guide](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/multi-schema); [Prisma ORM 6.13 release material](https://github.com/prisma/web/blob/main/apps/blog/content/blog/orm-6-13-0-ci-cd-workflows-and-pgvector-for-prisma-postgres/index.mdx) | Official materials document `schemas` in the datasource and `@@schema` on models/enums; the release material says multi-schema became generally available in Prisma ORM 6.13. The guide supports cross-schema relations and Prisma Migrate for documented PostgreSQL configurations. | Select the exact `prisma` and client versions, validate all ten schema names, generated client, relation naming, migrations, provider behavior, and any custom SQL. Do not infer Prisma ORM 8 compatibility from a v7 guide. |
| Prisma Migrate command workflow | [Production/development migration workflow](https://www.prisma.io/docs/orm/migrations/applying-a-migration) | Prisma ORM 7 guidance uses `prisma migrate deploy`; current ORM 8 release-candidate documentation describes planning migrations and applying with `prisma db migrate`. These workflows are not interchangeable command recipes. | Pin the Prisma major before authoring CI/deployment instructions. Test fresh database, upgrade path, migration-history integrity, production connection, lock risk, and recovery using the exact CLI version. |
| Prisma transaction API | [Transactions](https://www.prisma.io/docs/orm/fundamentals/transactions) | ORM 7 and earlier commonly use `$transaction`; current ORM 8 RC documentation uses `db.transaction`. The ORM 8 documentation does not expose `isolationLevel`, `timeout`, or `maxWait` options and describes setting isolation at the start of the callback; its transaction layer does not automatically retry write conflicts. | Choose protocol from the pinned ORM API. Verify isolation and connection behavior; implement bounded retries only for classified retryable failures and idempotent operations. Test under PostgreSQL. |
| Better Auth Prisma adapter | [Official adapter guide](https://www.better-auth.com/docs/adapters/prisma); [adapter peer dependencies](https://github.com/better-auth/better-auth/blob/main/packages/prisma-adapter/package.json) | Current adapter guidance is written for Prisma 7 and distinguishes Prisma 6 or earlier. The reviewed adapter package declares Prisma 5, 6, and 7 peer ranges; Prisma 8 is not listed. Prisma 8 is described as a release candidate in current Prisma documentation. This is **not evidence of Prisma 8 compatibility**. | Do not pair Prisma 8 with this adapter without an updated official support declaration or successful, version-pinned integration validation. Review the generated auth schema and deliberately place auth models within the ten-schema ownership policy. |
| Better Auth sessions/cookies | [Session management](https://www.better-auth.com/docs/concepts/session-management); [cookies](https://www.better-auth.com/docs/concepts/cookies) | Server-side session validation is documented. Optional cookie caching can avoid a database lookup and may delay revocation until cache expiry; cookie defaults, session lifetime, freshness, secure attributes, and origin checks are library/configuration details, not SAP Core policy. | Select explicit session lifetime/freshness/revocation rules; validate the actual deployment’s cookie/origin/CSRF settings and high-risk operation freshness against the pinned release. |
| Better Auth email/password | [Email and password](https://www.better-auth.com/docs/authentication/email-password) | Email verification and reset flows depend on configured delivery callbacks. The repository correctly defers provider selection; there is no production email delivery implementation. | Product/operations must approve delivery, abuse controls, monitoring, sender/domain policy, and recovery behavior before enabling production flows. |
| CASL authorization | [CASL v6 guide](https://casl.js.org/v6/en/guide/intro/); [official project docs source](https://github.com/stalniy/casl/blob/main/docs-src/src/content/pages/advanced/ability-to-database-query/en.md) | Project docs describe action/subject checks and a `rulesToQuery` helper for converting conditions to database query predicates. The hosted v6 page did not return readable text to the page reader; Context7 retrieved the official project repository’s documentation. No Prisma-specific query translator or installed CASL version was validated. | Pin CASL; test allow/deny conditions and ensure database filtering matches policy. Do not fetch broad results and filter after serialization or rely on client ability state. |

## Compatibility gates

1. Add a real application manifest and lockfile; pin Node.js, Next.js/React, Prisma CLI/client, Better Auth adapter, CASL, and other selected dependencies.
2. Confirm that the selected Prisma ORM release and Better Auth adapter support one another. If Prisma 8 is considered, resolve its release status and adapter support first.
3. Validate the complete ten-schema mapping and auth-model placement with the selected Prisma schema/generator. Test generated client output and migration SQL against a disposable PostgreSQL 17 instance or the actual provider major.
4. Exercise representative posting, stock transfer, key allocation, and authorization operations under concurrent requests; do not infer these properties from schema validity or a single-user test.
5. Verify provider-specific pooling, migration connection, backup/restore, and credential separation before production.
